# Dispatch and effect safety — 2026-11-19

Assigned Paperclip issue creation uses `issue-create:<run>:<node>:<attempt>:<phase>` as its durable external operation identity. The operation stores the complete request before sending and permits exactly one automatic send. A thrown call or an interrupted process leaves `unknown`; elapsed time, restart, and an empty origin lookup do not authorize a replay. A trusted host lookup can confirm a single matching issue only after checking company, origin, assignee, parent, and project; duplicates or mismatches remain blocked. Existing successful operations retain their result. An operation ID reused with a changed request fails closed. Confirmed outcomes cannot be replaced with conflicting outcomes. Sibling dispatches continue when an effect returns unknown or ambiguous.

`normalizedState` exposes requested, admitted, dispatched and started separately. A wakeup response or run ID alone is not evidence of start. Started requires the exact issue, agent, and execution checkout to be verified by the host and persisted; older records remain dispatched until verified. Workspace admission is displayed as `legacy_unmanaged` or `exclusive_required`; the latter is an admission requirement, not a claim that a workspace is fenced. Assigned issue creation remains the only wakeup mechanism; this change does not add a second wakeup call.

The effect ledger is wired to assigned issue creation only. It does not claim to cover merge, deploy, arbitrary tools, or workspace finalization. Its retry budget is deliberately one send, with no automatic replay even after confirmed failure; a separate governed recovery mechanism would be needed to authorize a new operation. Historical issues created before migration are not retroactively represented in the ledger. Request changes during recovery cause a conflict. The origin search relies on the host's issue API and its returned identity; eventual consistency cannot establish failure. Workspace finalization and external dependency facts require trusted integrations and are not inferred from user input.

Validation: `node --test tests/plugin/workflow-dispatch.test.mjs tests/plugin/effect-ledger.test.mjs tests/e2e/dispatch.test.mjs tests/e2e/dispatch-admission.test.mjs tests/e2e/dispatch-limit.test.mjs` passed 15 tests including the linked-workflow suite; one opt-in PostgreSQL test was skipped. `npm run build` completed, although PowerShell emitted a nonfatal npm profile access warning. Tests cover unknown outcome across subsequent dispatch calls, single-send behavior, request and outcome conflicts, checkout proof, and duplicate or mismatched origin results. PostgreSQL migration and process-restart behavior need a live PostgreSQL integration run; the unit-backed recovery test models a subsequent caller using the same persisted record.

The optional trusted `host.assessGraphDispatchLifecycle` hook supplies dependency facts (`before_work`, `before_review`, or `after_review`) and workspace finalize outcome. Review does not wait on after-review blockers. A pinned node declaring `hostLifecycle.privileged: true` is blocked before work unless the host reports applicable dependencies ready and finalization confirmed successful. Without the trusted hook such a declaration blocks; undeclared legacy nodes remain unmanaged. The hook is an adapter contract: no current host integration is claimed, and it does not itself finalize a workspace or gate external effects performed elsewhere.

Retry retirement and its run digest now derive from the same durable state snapshot. Core compares that digest before a new mutation; identical committed idempotent replays return their recorded result. A deterministic barrier test covers the concurrent replay race, and a separate test confirms a fresh authorized request can advance after a stale digest rejects a previously retired attempt.
