# Contract merge Host action

Trusted Host code calls `mergeContract` from `dist/host/contract-merge.js` with its configured project, run and PR identifiers, gate decision ID, and the approved manifest's artifact ID, immutable revision ID and bytes. The project supplies `id`, `repository`, `ownerId`, and optionally `contracts_root` (default `knowledge/contracts`). A new merge requires the root to be printable ASCII; spaces are allowed. Recorded and recovered receipts still return for a legacy root. Publication and implementation merges require the trusted ADLC Pack's contract layout v2 helpers. The technical path also requires a configured `ctoId`.

Product publication requires the current human `requirements-acceptance` decision with outcome `accept` from the configured owner. Technical publication requires the current CTO `technical-contract-approval` decision with outcome `accept`. The action matches the decision to the current completed gate attempt and checks its evidence for the manifest artifact ID and revision. Configured G2 gates collect the decision through a revision-bound Paperclip confirmation. Product publication may include `design/interaction.md`, because G2 approves the interaction design with the PRD. In manual mode, design publication requires the current human `g3-visual-approval` decision with outcome `approve` from the configured owner, as produced by the Creative `g3-visual-contract` graph. It may change any `design/` file except `design/interaction.md`, because a behavior change returns to G2.

## Enable G2 publication

1. Install the dedicated GitHub App on the repository. Configure the company-scoped `githubApp` with `appId`, `installationId`, and `privateKeyRef`. Set the project `repository` to GitHub's canonical full name and set `githubRepositoryId` to its numeric ID. Configure `ownerId` for the human approver and recovery operator.
2. Put a valid `INDEX.json` on main under the project's contracts root. Use `[]` for a new repository. The default root is `knowledge/contracts`. The reference profile requires ASCII contract path segments.
3. Run the [paired transport probe and deployment acceptance](github-merge-journal.md#installed-pair-transport-probe) before recording `githubTransportAttestation`. Publication stays blocked on the installed Paperclip SDK until the worker can verify the running host version.
4. Select `contractPublication.validatorId: adlc-g2-reference-v1` and set `contractPublication.g2` to `true` when the deployment is ready. The ID prefix defaults to `PRC-`. A custom `contractIdPrefix` has one to ten uppercase letters or digits, starts with a letter, and ends in a hyphen. The scheduled worker reports G4 and G3 as `blocked-config: publication-validator-unavailable`.

The product author or operator opens the proposal PR against current main and supplies its number to `publish-baseline`. Start from the approved Decision Record and the exact frozen manifest. The manifest must specify `contract.type`, `contract.slug`, and the digests of `prd` and `acceptance.feature`. The optional `interaction-design` key supplies `design/interaction.md`. Use one unique `@AC-<positive integer>` tag on each Gherkin scenario or scenario outline. Criteria follow the scenario order in the approved feature file. Write UTF-8 files with Latin-script letters. JSON checks include decoded keys and string values.

The compiled author helpers are in `dist/host/contract-publication.js`. Use `contractProposalLocation` for the branch and folder and `derivePublication` to generate the proposed changed files from trusted inputs. First publication derives the ID from the Decision Record and uses the approval hour in UTC. A replacement uses the ID and folder of the active product receipt and sets the approved manifest's `supersedes` to that receipt's commit. The PR must contain exactly the necessary adds and modifications and match the profile's bytes. Start with a fresh G2 approval when the merge request needs new approval.

## GitHub adapter

The action uses the following injected methods. Blob values are raw bytes or UTF-8 strings. Digests are lowercase SHA-256 hex.

- `getRef({ repository, ref })` resolves `refs/heads/main` to a commit SHA.
- `getPullSnapshot({ repository, pullNumber, baseSha })` supplies `baseRef`, `baseSha`, `headSha` and the complete diff between those SHAs as `changes`. Each change includes `path`, `mode`, `status`, `bytes`, and `previousPath` when applicable. Establish that the pinned main commit is an ancestor of the proposed head. The action permits regular-file additions and modifications.
- `loadValidator({ repository, ref })` selects trusted, installed Core or Pack code and pins repository project data to the supplied main SHA. Its `recompute({ repository, baseSha, headSha, contractsRoot, section, manifest })` method reads Git content at the pinned revisions and treats the head as data. It validates Pack formats, deliverable mappings, project-specific CI paths, file types and lock and index semantics. It returns the validated lock's `contractId` and `supersedes`, the active immutable `currentRevision` from main (null for initial publication), a `deliverables` map from manifest key to proposed published bytes, and a `changes` map from repository path to independently recomputed bytes. Include every required publication change, including generated criteria, lock and index changes where applicable. Generate those bytes from approved immutable revisions and trusted main state. Throw on validation failure.
- `merge(request)` merges the given pull request at the pinned head and main SHA. Serialize operations on a target and reject a changed head or base. Return the merge commit SHA. Make the operation idempotent for the full publication identity, including the run, decision and manifest digest. Recheck main immediately before the merge and verify the resulting commit parents.
- `getMergeReceipt(request)` recovers a successful operation by its full publication identity. It returns `{ baseSha, headSha, mergeCommitSha, contractId, supersedes }` or null. The adapter authenticates the receipt as its own successful merge for the same request. This supports retries after a failed run write.

The action records the receipt and a `contract.merged` audit event in one Core store update. The event carries the run ID and receipt fields, including `mergeCommitSha`. Downstream consumers use that event as the publication signal. The technical publication event carries the fields used to start G-T2.

GitHub Free private organization repositories lack branch protection and rulesets. The bot enforces the checks before its merge. Other users and tokens with write access can bypass the bot.

### GitHub App adapter

The worker supplies a repository-scoped installation token provider, the compiled validator, and the database-backed journal writer to `createGitHubAppAdapter`. The validator reads project data at pinned main. It matches bytes from each statically mapped PR path to its approved digest. The writer fences the current graph revision and admitted queue fingerprint when accepting intent and rechecks project policy and the PR before PATCH. The adapter also supports the existing direct Host mode with a caller-supplied receipt store.

The adapter creates a temporary ref at the pinned main SHA, merges the pinned PR head into it and verifies the resulting commit's two parents before advancing main. It uses a non-forced ref update so an incompatible concurrent advance fails. The durable journal records the prepared commit before the ref update and can recover it from main's ancestry. Retain `mergeActorLogin` for reconciliation of legacy journal entries.


### Implementation merge

G5 binds the implementation PR head and verification manifest revision to the current Decision Record. Core combines the trusted Pack floor with one `implementation-risk` decision evidence item carrying `riskLevel` and a subject reference to that PR head. The GitHub adapter reads changed npm dependency files at the pinned base and head. A trusted installed validator may supply broader dependency coverage. Unavailable risk data disables agent approval.

Core requires a passing verification manifest and, for agent approval, the latest completed attempt of each blocking review node (`interrogate`, `deep-review`, `edge-cases`, `security-review`) must record `output.reviewDisposition = { headSha, status: "pass" }` for the verified head. Alternatively, as in `verification@0.1.9`, the latest completed `review-head` attempt records `output.adlcProductMethods.pr_reviews = { headSha, reviews }`, in which every blocking review is `completed` and each finding is a nit/P3 or `fixed`. Core forwards the project `ciPaths`, `riskRules`, and `neverAutoMerge` to the Pack risk table. The trusted Host supplies `authorAgentId`. Assisted approval requires an independent CTO/CAIO and low final risk. All Pack never-auto-merge hits require the configured owner. Receipts retain the computed risk, matched rules, categories, evidence completeness, effective mode and whether agent approval was used.

G5 reads the pinned product criteria through the installed validator and requires every scenario and configured dimension. It checks both names of renamed paths and rechecks CI on the approved head immediately before advancing main. If the project configures required checks, each named check must succeed. Otherwise every reported check must succeed, with at least one check reported. Manual mode requires the configured owner.

In assisted and enabled full-auto runs, `g3-visual-auto-approval` can also authorize a design director. The immutable manifest and the current completed `design-audit` output must both declare unchanged behavior. The manifest must be in-system, the audit must have no P0 or P1 findings, and the decision must cite that audit revision. The audit binds the canonical JSON digest of the manifest. The configured owner can approve either G3 decision type. A configured project's automation mode sets the ceiling for new ADLC and Creative runs, and full-auto requires `allowFullAuto: true`.

The contract merge receipt and event carry the permanent contract ID and superseded commit from the trusted validator. Core tracks supersession by project and commit, including when the replacement has a different contract ID. G5 requires a fresh decision, verification attempt and review after a pin update. Freezing a contract holds all of its sections. After PE reassessment the Host calls updateContractPins with the paused run digest. An owner can then resume the run after the freeze is lifted and all pins are current.

The installed validator provides `readVerificationCriteria({ contractId, contractsRoot }, { readFile })` to resolve the contract directory and return the validated `product/criteria.json` rows. The adapter binds all reads to the pinned main SHA.
