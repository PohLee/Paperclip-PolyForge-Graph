# ADLC security, skill evaluation and small-change pilots

## Security and run lessons

For changes to permissions, trust boundaries, sensitive data flows or external integrations, the ADLC 0.3.5 guidance puts the threat model in the versioned technical design. QA uses the existing failure-modes and implementation-feasibility axes to check the proposed mitigation and its verification. Readiness names the owner and check for each material control. The Pack supplies instructions and the existing design disposition handles missing evidence. This first increment adds no new automatic security certification.

A human owner can record a lesson on a project-linked Graph run with a saved artifact. Open **Graph runs**, select the run and expand **Record a run lesson**. Choose the exact attempt and artifact, describe the observation and suggest a change. Find it again in **Company operations → Knowledge**. The Graph stores the original attempt and artifact version, even when they are superseded. Lessons are advisory and belong to one project. Agents only receive lessons for projects in which they have an authorized dispatched run.

The same operation is available through the authenticated plugin company endpoint with operation `record-run-lesson`. Supply `companyId`, `projectId`, `runId`, `nodeId`, one-based `attemptNumber`, `candidate: { id, version }`, `title`, `observation`, `suggestedChange`, `reason` and `idempotencyKey`. Read via `query-knowledge` with the project ID and `kind: "run-lesson"`. An observation can be saved after one run. A change to a mandatory guardrail follows the existing graduation process.

## Skill and role evaluation

Run the same pinned fixture tasks on the old and new instructions. The included scenarios cover repository preflight, security readiness, a design control, conflicting ticket write scopes and a revised review candidate. Use an isolated workspace and a fresh session per trial.

```sh
node scripts/eval-adlc-skill.mjs BASELINE_PACK_JSON CANDIDATE_PACK_JSON CONFIG_JSON LOCAL_ADAPTER
```

The config pins `model`, `toolsVersion`, full `repoSha`, `repetitions` and a `target` such as `{ "skill": "engineering-delivery" }` or `{ "role": "principal-engineer", "document": "instruction" }`. For a skill, the evaluator runs the relevant fixed scenarios. Role instruction evaluation runs the fixed suite. Use the two generated ADLC `pack.json` files. The report records both Pack hashes and instruction hashes. The adapter runs with local code permissions.

The adapter exports `runCase({scenario, variant, settings, repetition, pinned})` and `observe({scenarioId, observation, variant})`. Supply only `settings.instructions.content` as the changed instructions. Keep the repository, tooling and model fixed. Return the recorded transcript or artifact references from execution. The separate `observe` reads those records and returns `{signals, evidence}`, with a nonempty list of evidence references. Signal names and critical failures are defined in `src/host/adlc-skill-eval.mjs`. Record a failed or interrupted trial as invalid and rerun it with its original fixture inputs. The CLI exits unsuccessfully when the candidate produces an invalid trial, a critical regression or a failing trial.

## Small-change pilot

ADLC Pack `0.3.7` ships `small-change@0.2.1` as an opt-in pilot. A human owner requests a standalone manual run. Before dispatch, the host confirms the active product approval, versioned requirement, acceptance criteria, isolated checkout and base commit, exact file paths, one-commit rollback, executable check and named independent reviewer. A defect also needs a verified reproduction. Permissions, sensitive data, migrations, shared contracts, external integrations, production operations and changes to approved behavior go through standard implementation. Missing or unknown scope evidence follows the same route, subject to the ordinary standard start requirements.

The producer submits a full commit SHA as the `implementation_candidate` and a `test_report` for that SHA. The host snapshots the producer's commit, index and object bytes through filesystem reads before running any Git inspection. Worker Git runs only against fresh temporary metadata with host-defined configuration and a sanitized Git environment; it never loads the producer's configuration or invokes Git or upload-pack in that repository. The host verifies copied object integrity with Git fsck and requires a clean checkout, one direct child of the admitted base, the approved modified paths and file modes, and the operator's configured scope rule for the changed lines. It then fetches the submitted SHA and its direct parent only from the validated, worker-owned metadata snapshot into a separate temporary checkout, detaches at that SHA and runs the configured check there. Ignored producer build outputs and dependencies are not copied. Each concurrent verification has its own checkout and Git metadata; the host removes it after the check, including on failure, and treats setup or cleanup failures as missing proof. Missing proof, failed checks or out-of-scope changes stop the pilot and open a linked standard implementation run. Graph runs links to the original attempt, including its candidate, submitted evidence, diff assessment and any verified check reference. When trusted inspection routes to standard, malformed artifact identities or missing versions remain in the rejected attempt as submitted evidence and are not published as accepted node artifacts. Normal and eligible submissions still require artifact identities and versions. If ordinary start policy blocks the standard run, the original Graph preserves its history and shows the blocker. The owner can start standard implementation with the current required context and use the original run ID as `parentRunId` to retain lineage.

A passing candidate proceeds through one producer self-review and one review assigned to the independent Principal Engineer Agent pinned at admission. The existing final implementation acceptance gate requires a human owner. A revised candidate goes through a new diff review.

### Isolated host configuration

The pilot is disabled when `polyforge.small-change-pilot.mjs` is absent from the installed plugin root. For an isolated Host only, the operator places a trusted module at that location, outside the candidate checkout. Its default export declares `companyIds` and `lookup({ companyId, projectId, issueId })`. The lookup returns the approved checkout `path`, stable `key`, `allowedPaths`, `requirementId`, `requirementVersion`, `approvalId`, `reviewerId`, `checkId`, and `reproductionRef` for defects. The `reviewerId` must match the configured ADLC principal engineer, with a separate lead engineer bound to produce the work. A lookup returns no scope for tasks the operator has not approved.

The lookup also supplies `reviewDiff({ base, head, diff, patch })` and `check({ cwd, base, head, checkId })`. The first function confirms the patch against the approved requirement and returns `{ outcome: 'within-scope', headSha, evidenceRef }` only with evidence for the exact SHA. The check runs the operator-selected verification against the fixed commit in isolation and returns `{ id, headSha, result: 'pass', evidenceRef }` only after success. The host accepts call parameters from its own resolved checkout and installed module.

The `check` signature is unchanged, but `cwd` now names the disposable detached checkout. Existing adapters must run commands in this supplied directory and prepare any required dependencies or generated outputs there. The two-commit checkout supports both branch and detached producer HEADs and supplies the exact `head` and `base` commits, without unrelated refs or older history. The checkout does not inherit repository-local Git configuration, linked worktrees, submodule working directories or ignored files from the producer. Checks that need older history, tags or branch refs must prepare them explicitly from a trusted source or use standard implementation. Configure required tooling explicitly; use standard implementation when isolated verification cannot be reproduced. Checks must leave tracked files, detached HEAD and the commit unchanged, stop and await their subprocesses before returning, and persist logs or evidence outside the temporary directory before returning an `evidenceRef`. Unignored generated files also make verification fail. The producer checkout is never cleaned or switched by verification.

Inspection supports ordinary SHA-1 repositories, packed refs and ordinary loose or packed objects. A linked worktree or separate Git directory requires the trusted lookup to pin its canonical absolute `gitDirectory`; a shared object store also requires the canonical absolute `commonDirectory`. Producer `.git` and `commondir` pointers must match these operator paths. Symlinked metadata directories/files, multiply linked metadata files, alternate object stores, split indexes, incomplete/shallow source histories, promisor stores and unsupported storage extensions fail closed and route to standard implementation. Each filesystem snapshot is bounded to 256 MiB and 50,000 files. Concurrent metadata changes or incomplete copies also fail closed; verification never falls back to producer-side Git. Producer Git configuration, global ignore rules and `.git/info/exclude` do not define cleanliness. Worktree `.gitignore` rules apply, and the host uses Git's built-in input line-ending normalization. A fresh tree index prevents producer index flags or cached file statistics from hiding edits; staged changes are checked separately.

The installed operator module, Git executable and worker environment must be protected from the producer. The existing trusted `check` adapter must execute candidate-controlled commands in an actual process/filesystem/credential isolation boundary that denies access to the worker, its inspection metadata and operator configuration. Merely changing `cwd` or sharing the worker's credentials does not establish that boundary. If the deployment cannot provide it, leave this pilot unconfigured and use standard implementation. The host never runs Git against the check's writable metadata after execution: it verifies files through the separate inspection repository and reads detached HEAD as inert bytes. This prevents check-modified Git configuration from becoming worker execution, but does not itself sandbox candidate code.
Start through `graph-command` with `operation: 'start'`, `graphId: 'small-change'`, `mode: 'manual'` and an `idempotencyKey`. Supply ordinary implementation context and `input.pilot_scope` with `kind`, `baseSha`, `paths`, `rollback: 'single-commit'`, `reviewer`, `checkId`, `approvalId`, and `risks`. Explicitly set `permissions`, `sensitiveData`, `migration`, `sharedContract`, `externalIntegration` and `productionOperation` to `false`. For `kind: 'defect'`, supply the operator-verified `reproductionRef`.

```sh
node --test tests/core/adlc-pilot.test.mjs tests/core/small-change-git.test.mjs tests/core/adlc-skill-eval.test.mjs
```

The isolated tests exercise the trusted Pack adapter and Graph engine against temporary Git repositories. The plugin build also starts the bundled worker over JSON-RPC. The standard-versus-pilot comparison for elapsed time, review effort, corrections and missed defects requires a real Runner and a configured evaluation adapter. The pilot is opt-in per company on an isolated Host.

See the [controlled dynamic workflow plan](controlled-dynamic-workflows-implementation-plan-2026-11-08.md#adlc-工单-dag-试点) for the separate issue-level fan-out and recovery trial.
