# Paperclip PolyForge Graph MVP 需求基线

日期：2026-10-27

以 Paperclip 为底座，为一人公司提供可以配置、追溯和持续调整的 Agent 工作平台。首个领域应用是 Agentic Development Life Cycle（ADLC）。核心插件负责通用执行能力，ADLC Pack 提供角色、方法、Graph 和领域规则。

本基线承接“Paperclip agents”聊天中的目标及本次需求确认。标为“已确认”的内容来自用户明确要求；标为“建议细化”的内容用于使需求可执行，尚未作为用户已批准的具体规则。本文描述目标行为与验收要求。

## 项目边界

**已确认：一个核心插件，加一个独立的 ADLC Pack。**

| 项目 | 目录 | 职责 |
| --- | --- | --- |
| 核心插件 | `D:\Projects\00.Own\05.AI-Ops\Paperclip-PolyForge-Graph` | Pack 接入、Graph 执行与恢复、角色与运行环境绑定、决策与证据追溯、Paperclip 集成 |
| ADLC Pack | `D:\Projects\00.Own\05.AI-Ops\Paperclip-PolyForge-Graph-ADLC` | ADLC 角色说明、skills 组合、Graph、决策模式、产品与工程验收规则、场景验证 |

职责拆分的具体边界属于建议细化：领域流程与角色判断方法由 Pack 发布，核心插件提供这些规则所需的执行与记录能力。Core 保持可承载其他领域 Pack 的边界。

## MVP 场景范围

**已确认：Graph 随 ADLC Pack 发布；先验证 MVP 场景，验证后逐步微调各自 Graph。**

原始目标中已描述三张 Graph：

| Graph | 工作内容 | 交付结果 |
| --- | --- | --- |
| UI/UX Design | 按 none、minor、major 分流；按分支需要进行研究、候选设计、独立筛选、原型比较和最终决策 | `final_design_identity` |
| Implementation | 制定计划，前后端实现与测试并行，ALL 汇合，独立实现评审，验收或返工 | `implementation_acceptance` |
| Verification | 对固定候选产物并行进行 QA、安全评审和回归测试，ALL 汇合后验收 | `acceptance_decision` |

Graph 中的人工接受节点依决策模式启用；执行者和上级的职责适用后文评审规则。

**范围假设：** 用户随后要求开始开发与 Docker 验证，当前按以上三张 Graph 开展 MVP 场景验证。“三项”是否还包含市场研究、自动排期、自动发布仍待明确；这些扩展不作为当前实现已覆盖的内容。

## Agent 与角色配置

原始目标包含以下 11 个常驻角色，构成 ADLC 团队蓝图：CPO、内部产品分析师、外部产品分析师、Product Manager、Product Owner、UI/UX Designer Lead、CTO + CAIO、Principal Engineer、Lead Engineer、QA Engineer、Security Engineer。

**已确认的组织层级：** “Paperclip agents”原始需求的编号 1、1.1–1.5、2、2.1–2.4 定义以下汇报关系；用户于本次修正中指出全部角色显示 `Reports to Board` 不符合该结构。

| 组织上级 | 直接下属 |
| --- | --- |
| Board（人类所有者） | CPO、CTO + CAIO |
| CPO | 内部产品分析师、外部产品分析师、Product Manager、Product Owner、UI/UX Designer Lead |
| CTO + CAIO | Principal Engineer、Lead Engineer、QA Engineer、Security Engineer |

Pack 使用 `reportsToRole` 表达组织上级，集成层将角色解析为同一公司中的实际 Paperclip Agent ID，保存到 `reportsTo`。CPO 和 CTO + CAIO 的组织上级为 Board，在宿主中使用空的 Agent 上级引用。

组织层级与产物评审分开保存：现有 `supervisorRole` 表示产物评审职责，例如分析师的产物可由 Product Manager 评审，Lead Engineer 的产物可由 Principal Engineer 评审。Graph 仍执行原有的独立评审身份隔离和决策规则。

每个 Agent 可以拥有 `soul.md`、`role.md`、`goal.md`、`instruction.md`，以及一个或多个可调用 Graph、skills、tools、harness/runtime。Graph 选择遵循角色 instruction。角色和实际执行实例的绑定应支持调整。

**已确认：** 同一 Agent 可以承担多个角色；需要独立评审的环节必须明确隔离要求。

**建议细化：** Pack 对每类重要产物声明执行角色和上级评审角色。独立评审使用与实现分开的执行实例或会话，保留实际 Agent、角色与运行身份，并给予评审者直接检查产物及证据的权限。同一个实现执行实例不能通过切换角色名称完成自己的独立批准。

Design Graph 中的 Head of Design、Design Evaluator 需要在 Pack 中绑定到合适的职责或独立执行实例；是否新增常驻 Agent 留待 Pack 设计确定。

## 决策模式与配置

**已确认：** 支持从人工决策、半自动到高度自动化的全局模式。通过“决策类型 × 模式”配置行为，规则保存在各自 Agent 的 Markdown 文档中，必要时独立为 `decision_model.md`。

**建议细化：** 统一采用 `decision_model.md` 作为文件名；角色文档引用它。规则用文档内可解析的结构描述，并保留可读的说明，具体格式在技术设计中确定。

每条规则至少能表达决策类型、当前模式、允许的决策角色、所需证据、继续条件，以及需要升级给上级或人类的条件。权限判定与质量验收分别配置。

建议纳入的决策类型包括产品范围变化、优先级调整、技术方案、设计选择、Graph 分流、评审结论、返工、验收、产品决策替换，以及被纳入交付范围的合并和发布动作。具体矩阵值由 Pack 定义，本基线不预先授予这些动作自动执行权限。

核心插件需要校验实际决策是否满足规则。需要人工决定的事项必须关联真实人类的操作身份；Agent 提交的建议不能被记为人类批准。

## Graph 与运行版本

**已确认：** Graph 有版本；运行中的任务固定使用启动时的版本。MVP Graph 通过 ADLC Pack 发布，验证后的流程调整随新 Pack 版本交付。

**建议细化：** 一个运行记录完整的 Pack 与 Graph 版本，并保存所用 instruction、skill、决策规则及角色与 runtime 绑定的快照或内容摘要。旧版本被更新后，仍能解释已有运行的行为。

Graph 与其引用的子图都应解析到具体版本。升级后，新运行使用选定的新版本，暂停后恢复的运行继续使用原版本。MVP 不以运行中自动改写 Graph 作为默认行为。

## 重要产物的评审与交付

**已确认：** 执行者交付重要产物前先自审，直到没有 P0/P1，或者达到约定的轮次边界；然后交付上级。上级作为独立评审者和决策者，决定返工或继续。

**建议细化：** 将“超过 5 round”落实为每次提交最多 5 轮自审。每轮记录被检查的产物版本、发现的问题、修复动作和结果。第 5 轮结束仍存在 P0/P1 时，提交剩余问题及证据给上级，不再自行追加第 6 轮。

1. 自审无 P0/P1：连同全部自审记录交给上级独立评审。
2. 自审达到上限仍有 P0/P1：连同未解决问题交给上级裁决；轮次耗尽本身不构成通过。
3. 上级要求返工：记录原因、需修改范围、相关问题和需要重新验证的证据。
4. 上级同意继续：记录决定及其依据；若保留已知问题，必须显式记录处理方式，并满足该决策类型的权限与质量规则。

P2/P3 等剩余问题随产物保留。上级是否有权接受特定剩余风险，由决策矩阵规定。一次返工可以产生新的提交尝试，自审历史不能清空；总返工次数或成本边界需在 Graph 配置设计时确定。

## CPO 与 CTO 分歧处理

**已确认：** 参考 PolyLens 的 resolution 方法。无法达成一致时，交给人类决定。

PolyLens 的 Collision Engine 比较双方在范围、时序、资源、风险和成功标准上的立场，对冲突去重和分类；相同的 GO、MODIFY 或 BLOCK 标签本身不足以证明不存在冲突。[Collision Engine](https://github.com/PohLee/PolyLens/blob/92ed5fadd31177f67166e855a6e7e56a8a79c767/engines/collision.md)

其 Synthesis Engine 按冲突类型处理：优先级可分阶段，范围可依据不可妥协条件收敛，风险可比较影响与可逆性，资源分歧可检查承诺及证据；无法解决的分歧保留待决状态并交给人类。[Synthesis Engine](https://github.com/PohLee/PolyLens/blob/92ed5fadd31177f67166e855a6e7e56a8a79c767/engines/synthesis.md)

**建议的 ADLC 适配：**

1. 保存 CPO 和 CTO 的原始立场、目标、约束、证据及不可妥协条件。
2. 建立冲突清单，按类型提出解决方案；必要时进行一次聚焦的质询与答辩。
3. 双方对解决后的方案重新给出意见，明确已解决事项和仍有分歧的事项。
4. 无法达成一致时，保存选项、取舍和未解决问题，暂停受影响的推进，等待人类决定。
5. 保存人类决定，更新当前方案，并根据决定继续或返工。

PolyLens 的 pre-fight 另有自动仲裁路径；本项目采用用户明确要求的“无法一致则人类决定”，即使处于高度自动化模式也保留这一升级条件。[Pre-fight 处理路径](https://github.com/PohLee/PolyLens/blob/92ed5fadd31177f67166e855a6e7e56a8a79c767/orchestrators/polylens-pre-fight.md)

## Graph 交接与证据有效性

**已确认：** MVP 先采用版本化产物交接及受影响证据重新验证的方式，后续再演进。

**建议细化：** 下游接收具体版本的需求、设计、实现候选产物和验收决定。测试与评审报告指向实际检查过的产物版本。实现发生变化后，旧版本的报告不能直接证明新版本通过。

需求或产品决策变化时，标记受影响的设计、实现和验收结果，确定需要重做的节点；MVP 可以保守地重跑受影响阶段，后续再优化粒度。失效报告仍保留在历史中。

## 产品决策与历史记忆

**已确认：** Memory 优先保存产品决策和历史更改记录，确保 Agent 理解功能存在的原因、既有约束及历史问题，防止修复缺陷时未经决策就改变或删除产品行为。

**建议细化：** 修改功能前，执行者读取与该功能有关的有效产品决策、变更历史和已知约束，并在提交中引用这些记录。需要改变原有产品行为时，先提出产品决策变更，交给对应的决策流程。

已批准的决策变更创建新记录，并关联被替代的旧决定；旧决定及当时理由保持可查。缺失相关上下文或存在冲突时，明确标记待澄清部分，不把“没有检索到”当作“没有既有约束”。

MVP 可记录对 instruction、skill 和 Graph 的改进建议。具体更新通过 Pack 发布流程生效；自动学习和自动发布的范围后续再定义。

## 所有决策可追溯

**已确认：** 所有人类与 Agent 决策必须记录并可回溯。这一要求同时覆盖通过、拒绝、返工、暂缓、升级和替换旧决定。

**建议细化：** 系统显式作出的产品、工程、流程、配置和授权决定，均产生持久的 Decision Record。记录结论、简明理由和证据，不要求记录模型内部思维过程。

每条记录至少包括：

- 唯一标识、时间、决策类型及状态。
- 实际决策者身份与其角色；人类操作与 Agent 执行可区分。
- 决策所处理的问题、候选方案、最终结论及理由。
- 所依据的产品决策、历史记录、报告及产物版本。
- 当时使用的全局模式、决策规则、Pack 和 Graph 版本。
- 相关项目、任务、Graph 运行、节点和执行尝试；不适用时允许为空。
- 分歧、已知风险、未解决问题和需要再次检查的条件。
- 被替代的决定、后续修正及产生的实际工作或产物引用。

记录采用追加与关联修正的方式，避免用覆盖或删除抹去历史。已生效的批准必须有已保存的记录；记录失败时，依赖该批准的推进保持等待。重复回调可去重，同时保留真实发生的后续决定。

用户应能从功能或变更查看“为什么这样做、谁作出决定、依据哪个版本、影响了什么”，也能从一个决定找到对应产物和执行结果。长期记忆中的摘要要能链接回原始决定与证据。

## MVP 验收场景

以下为上述需求的建议验收方式，场景范围需与前述“三项”澄清结果对齐。

| 场景 | 预期行为 |
| --- | --- |
| 装配 ADLC Pack | 角色、说明、skills、Graph 和运行环境绑定可以配置；实际执行者获得所需上下文与能力 |
| 升级 Graph | 已运行及暂停中的任务保留旧版本；新运行可选择新版本 |
| 自审无 P0/P1 | 进入上级独立评审，并保留自审记录 |
| 第 5 轮仍有 P0/P1 | 携带问题升级给上级，不因达到上限自动通过 |
| 独立评审失败 | 根据记录的原因返回对应工作，保留前一轮产物和证据 |
| CPO 与 CTO 持续分歧 | 保存双方立场和解决尝试，等待人类决策；决定后可以恢复 |
| 修复缺陷涉及产品行为变化 | 引用原有产品决策，先完成必要的变更决策，再实施行为变化 |
| 被验收代码再次变化 | 旧证据仍可查询，新候选产物按规则重新验证 |
| 人类与 Agent 分别作出决定 | 均可查到身份、理由、规则版本、证据和受影响的产物 |
| 决策被替代 | 保留旧记录，沿替代关系查看完整历史及当前有效决定 |
| 中断、恢复或重复回调 | 不丢失待决事项，不跳过必要验收，不因重复通知重复生效 |
